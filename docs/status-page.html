The hard part

Linking three systems with no shared key

Nothing ties a Procore project to a QuickBooks job to a HubSpot deal. Everything downstream depends on getting that right, which is why the link is curated, not guessed. Matches resolve in strict order: a manual entry from the Controller always wins, then an exact project number, then a name match — but only when it is unambiguous.

If a project resembles two QuickBooks jobs equally well, the system does not pick one. That would be a coin flip dressed up as a decision, and it would silently attribute one job's cost to another job's revenue. It goes to a review page instead.

Projects that are missing a mapping still flow through, flagged. A gap makes a number visibly incomplete rather than quietly smaller — which is the difference between a report you can trust and one you cannot.

Findings

Four defects the live data exposed

Connecting to the real APIs found five bugs that no amount of offline testing would have caught. The first is the one worth understanding.

SILENT — WOULD HAVE PRODUCED WRONG NUMBERS

Budget columns named with spaces

Procore returns the money columns as Job to Date Costs, Revised Budget, Estimated Cost at Completion — with spaces. The standard way of reading those fields cannot parse a name with spaces; it returns nothing, which becomes zero. The result is a WIP schedule where every project shows zero cost, therefore 0% complete and 100% margin. It satisfies every accounting check and is completely wrong. Now read correctly, and pinned by a test against a real captured record so it cannot regress.

WOULD HAVE LOST DATA

One project could take down an entire feed

Procore answers with an error for any project that does not have a given tool enabled — which is normal, since not every job uses Financials. That error was aborting the whole feed, losing the projects that did have data. Now counted and skipped.

CONFIGURATION

Two connection details were wrong

The Procore URL was a browser address rather than an API address, so every request was malformed; the code now reduces whatever is entered to a valid endpoint. The vendor feed also pointed at a path that does not exist.

WOULD HAVE MISREPORTED ITSELF

The quality page reported the previous run

The report is meant to state its own trustworthiness. But the table feeding that page was built one step too early, so it always showed the last run's results — reporting zero warnings for a run that had just recorded one. Found by querying the live report rather than trusting the pipeline's green tick. It now rebuilds after the checks complete.

CAPACITY

The rate limit is 24× tighter than documented

Published guidance says 600 requests per hour. This tenant actually reports 25 per ten-second window. Code tuned for one behaves badly on the other, so the connector now reads the limit from each response rather than trusting a constant.

Needs you

What is blocking

QuickBooks authorisation. Intuit's security model requires a human to approve access in a browser once. It cannot be automated. Running python scripts/qbo_authorize.py opens the consent screen and stores the result; after that the connection renews itself.

One caveat worth knowing: QuickBooks issues a new credential every time the old one is used, and it expires permanently after 100 days of disuse. The platform stores each new one automatically and warns at 60 days, because the failure mode is an integration that works fine and then stops without notice.
